# 问题记录

## Q-20260723-008：为什么本地 HTTP 请求持续缓慢

- **日期**：2026-07-23
- **状态**：已解决
- **涉及模块**：FastAPI 生命周期、PostgreSQL、认证、Repository
- **用户问题**：感觉每次 HTTP 请求都有明显响应延迟，希望确认原因。
- **问题背景**：健康检查约 6ms，但每次 `psycopg.connect()` 实测约 491–719ms；受保护接口在认证和业务查询中会多次建立连接。
- **最终结论**：主要瓶颈是反复建立 PostgreSQL 连接。采用共享 Psycopg 连接池后，池借还实测约 0.02ms；同连接查询仍存在约 70–230ms 延迟，后续按 SQL 数量、索引和本机网络继续分析。
- **实现影响**：新增 `psycopg_pool`、连接池配置和 FastAPI 生命周期管理；不改变业务 API 或数据库 schema。
- **后续事项**：上线前依据 API 进程数与 PostgreSQL 最大连接数设置池上限，并增加请求/SQL 耗时观测。

## Q-20260723-007：新会话何时持久化

- **日期**：2026-07-23
- **状态**：已确认
- **涉及模块**：聊天页面、会话 API、会话持久化
- **用户问题**：点击“新会话”会先请求接口且产生空历史记录，希望首次输入并发送时再创建会话，并为后续 AI 流式回复保留这一流程。
- **问题背景**：点击即创建使界面产生等待，且用户没有发送内容也会留下无意义的会话。
- **最终结论**：新会话为前端本地空白状态，不调用创建接口；首次发送不带 `conversationId`，后端以单个事务创建会话和消息。后续 SSE 复用相同的首次发送语义。
- **实现影响**：新增统一消息接口；前端新会话不刷新历史列表；会话仅在首条消息成功后出现。
- **后续事项**：模型与 SSE 接入时补充流式事件和取消策略。

## Q-20260723-006：内置 AI 管家、默认清空和资料范围如何在阶段 2 落地

- **日期**：2026-07-23
- **状态**：已确认
- **涉及模块**：智能体、用户偏好、会话、数据库迁移、知识库设计
- **用户问题**：确认内置 AI 管家的稳定标识、`kind=builtin` 的含义、清空默认智能体的作用，以及资料范围的实施时机。
- **问题背景**：内置对象需要可被数据库关系稳定引用；默认选择与删除智能体是不同操作；知识库节点尚未建立，无法安全创建资料范围关联表。
- **最终结论**：内置 AI 管家使用固定 UUID，接口以 `kind=builtin` 表示系统内置类型；`DELETE /api/agents/default` 仅清空当前用户的默认设置，清空后聊天入口回退内置 AI 管家，删除默认个人智能体前必须先执行该操作；`knowledgeScopes` 延后至阶段 3。
- **实现影响**：迁移 `20260723_0002` 创建内置种子、用户偏好、智能体和会话基础表；新增智能体/会话 API 和默认删除保护；不创建 `agent_knowledge_scopes`。
- **后续事项**：阶段 3 在知识库节点实现后补充资料范围迁移、接口和校验。

## Q-20260720-005：首期智能体与知识库采用什么技术栈和实现路径

- **日期**：2026-07-20
- **状态**：已确认
- **涉及模块**：前端、后端、数据库、对象存储、OCR、模型服务、RAG、部署
- **用户问题**：基于已讨论的功能需求，确定项目的技术栈选型和实现方案。
- **问题背景**：项目当前只有 React/Vite 前端、FastAPI 后端、认证相关 PostgreSQL 表和 pgvector 扩展预留。首期需要支持多账号隔离、流式问答、会话历史、智能体配置、文件夹动态纳入资料范围，以及 PDF、Markdown、图片资料处理。
- **最终结论**：采用 ADR-005：继续使用现有 React + TypeScript + Vite、FastAPI、PostgreSQL + pgvector；新增 S3 兼容对象存储、Redis 后台任务队列、可替换的模型/Embedding 适配层。首期聊天模型供应商确定为 DeepSeek；Embedding 确定为 Worker 中本地运行的 `BAAI/bge-m3`。聊天界面采用 Ant Design X 与流式 Markdown 组件，业务数据流仍使用自有 SSE API。首期不支持图片、扫描版 PDF 或 OCR。首期受控使用 LangChain（模型、Embedding、提示词、文档对象、文本切分）和 LangGraph（显式聊天工作流与流式事件），但不使用通用 Agent/ReAct 循环，不让其接管权限、数据库访问或文件范围规则。
- **实现影响**：后续将增加会话、智能体、资料节点、文档、分块和配置关联等数据实体；需要版本化数据库迁移、对象存储、后台 Worker、流式消息接口和检索服务。
- **后续事项**：按 `docs/features/agent-knowledge-platform/` 实施，并在实施前锁定部署配置、迁移方案和依赖版本。

## Q-20260720-004：AI 管家、可配置智能体与知识库的首期范围如何确认

- **日期**：2026-07-20
- **状态**：已确认
- **涉及模块**：前端应用布局、会话、智能体、知识库、RAG、后端接口、数据库
- **用户问题**：希望以提供的五张原型图为基础，逐步明确 AI 管家问答、智能体创建和默认打开、智能体配置、知识库管理的详细需求、实现方案和技术栈。
- **问题背景**：当前项目仅有认证与受保护应用壳；AI 管家、智能体和知识库页面为空，`POST /api/chat` 只返回回显文本。原型明确了主要界面和部分会话隔离规则，现已通过需求与技术方案讨论完成首期设计确认。
- **最终结论**：已确认首期支持注册登录和多账号独立使用；除内置 AI 管家外，各账号的智能体、知识库、文件与会话数据均不得互通。AI 管家入口应按当前用户的默认打开设置显示智能体：未设置时显示内置 AI 管家；设置任一用户自建智能体后显示该智能体。无论当前显示内置 AI 管家还是自建智能体，右侧会话侧栏均只显示当前智能体自身会话，不显示其他智能体会话。知识库文件首期支持 PDF、TXT、Word（`.docx`）和 Markdown，不支持图片或扫描版 PDF。同一账号的知识库采用文件与文件夹管理；配置智能体时，用户可选择该账号知识库中的一个或多个文件和/或文件夹作为该智能体的可检索资料范围。因此同一文件或文件夹可被多个该账号的智能体复用，但每个智能体只能检索自己被配置选中的范围。选择文件夹时，文件夹后续新增的文件自动纳入该智能体的检索范围；直接选择单个文件时，只包含该文件。
- **实现影响**：将新增前端业务模块和页面、后端智能体/会话/检索模块、数据库实体及 API；所有用户自有数据查询和访问必须以当前用户为边界。智能体与知识库资料范围通过独立关联关系保存，而非复制文件或将整库硬编码到智能体配置中。
- **后续事项**：以 `docs/features/agent-knowledge-platform/IMPLEMENTATION_PLAN.md` 为实施顺序和阶段验证依据；会话删除、资料移动/删除及已删除智能体恢复/历史浏览须通过后续需求变更确认。

- **问题背景**：项目将新增知识库、RAG、LangChain 和 LangGraph 等跨模块能力，单纯给出实现结论不利于理解模块边界、数据流和技术取舍。

- **后续事项**：在知识库与智能体功能需求确认后，按 `docs/features/<feature-name>/` 建立正式设计文档，并以此约束实施与验收。

## Q-20260718-002：前端路由是否需要按认证与业务边界重构

- **日期**：2026-07-18
- **状态**：已解决
- **涉及模块**：前端路由、认证、应用布局
- **用户问题**：前端的路由配置是不是不合理，并要求基于诊断方案修改。
- **问题背景**：原实现通过用户状态切换两套 `Routes`，匿名状态下以 `*` 匹配全部地址，认证页模式不由 URL 表达，业务路径命名也不统一。
- **最终结论**：采用显式 `/login`、`/register`、`/app/*` 和独立 404 页；通过守卫组件隔离匿名与受保护路由，登录后恢复原目标地址，并将路径常量集中管理。
- **实现影响**：新增 `frontend/src/routes/`；导航与路由声明复用路径常量；原 `/robot/chat`、`/document` 不再是有效入口。
- **后续事项**：各业务页完成时，在 `/app/chat`、`/app/agents`、`/app/knowledge-bases` 下补充子路由，并评估路由级懒加载。
