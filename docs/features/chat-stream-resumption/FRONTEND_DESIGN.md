# 前端设计

## 1. 设计目标和范围

扩展 `useStreamingChat`，使其管理可恢复任务、事件序号和连接状态；页面与展示组件只消费统一状态。本次不增加重新生成按钮。

## 2. 涉及页面与路由

| 页面 | 路由 | 使用角色 | 页面职责 | 访问条件 |
|---|---|---|---|---|
| 正式聊天页 | 现有聊天路由 | 已登录用户 | 展示恢复中的回答与最终结果 | 当前用户拥有对应会话 |

## 3. 状态设计

每个会话流增加 `requestId`、`lastSequence`、`connectionState`、`reconnectAttempts` 和任务关联 ID。状态包含 `connected`、`reconnecting`、`reconnect_failed` 与终态；不将流状态写入全局 Store。

刷新恢复时，页面从会话详情中的生成中消息与恢复任务信息初始化 Hook，再自动发起订阅。每次事件解析成功后立即更新 `lastSequence`；序号小于等于该值的事件被忽略。

## 4. 数据请求与交互

1. 首次发送创建稳定 `requestId`，并以 `afterSequence=0` 建立流。
2. 非 Abort 错误触发 5 次重连，延迟为 1、2、4、8、16 秒。
3. 重连请求沿用原始 `requestId`、消息内容和最后成功序号，不能创建新乐观消息。
4. 刷新后自动调用会话详情与恢复任务信息，再执行第 3 步。
5. 达到重试上限后显示连接恢复失败，但保留已有片段；不出现手动恢复或重新生成按钮。

## 5. 页面状态

- 初始：正常历史消息。
- 生成中：显示当前回答与运行步骤。
- 重连中：保留当前内容并显示“连接中断，正在恢复回答”。
- 重连失败：保留内容并显示连接恢复失败。
- 完成/失败/超时/中断：按服务端终态展示，停止重连。

## 6. 测试重点

- 事件序号去重与断点后的文本拼接。
- 五次重连和延迟策略。
- 用户主动停止不触发重连。
- 刷新恢复不创建重复消息。
