# 后端设计

## 模块边界

- `retrieval/chunking`：混合切分与来源定位。
- `integrations/embeddings`：`bge-m3` 适配与模型缓存。
- `workers/embedding_tasks`：独立 `embedding` 队列消费、版本化索引任务。
- `repositories`：版本、分块、向量、范围展开和引用持久化。
- `services/retrieval`：候选融合、重排、文件级去重与限额、上下文构造和检索追踪。
- `integrations/reranker`：本地 BGE reranker 适配与模型缓存；不得暴露给聊天模型作为自由工具。
- 聊天工作流仅调用检索服务，不能直接查询向量表。

## 知识库优先运行流程

个人智能体或显式启用知识库的运行请求，先由运行图检查当前用户和智能体授权范围内是否存在 `ready` 且 `index_status=ready` 的文件。不存在时直接产生 `no_documents` 状态和固定说明；存在时，除资料目录查询外的每个问题都执行以下受控流程：

1. 向量与关键词检索分别召回最多 20 个分块，并在仓储层完成用户、资料范围和就绪状态过滤。
2. 服务层按 reciprocal-rank fusion 合并候选，不将原始分数跨检索器直接比较。
3. embedding Worker 使用本地 `BAAI/bge-reranker-v2-m3` 对最多 30 个候选计算查询-分块相关性。
4. 仅保留达到 `RERANK_MIN_SCORE` 的候选；按重排分数选择每文件最多 2 块、最终最多 5 块与 3 篇文件。
5. 记录候选、融合排名、重排分数、淘汰原因和最终采用来源；仅最终来源构造上下文、发送 `sources` SSE 事件并持久化引用。

最终没有有效来源时产生 `no_match` 状态和固定说明，不能调用聊天模型补充通用知识。只有最终来源存在时，才将受约束上下文交给模型生成带引用的回答。

资料目录查询使用确定性标记识别并读取真实元数据；该识别不决定是否检索，其他问题均固定为混合检索，因此不依赖大模型的意图分类。

## Worker 与模型

使用独立 embedding Worker 镜像/队列，避免 PyTorch 和模型加载阻塞文档解析 Worker。模型在 Worker 首个任务中懒加载为进程内单例；Hugging Face 缓存目录挂载为持久卷。初期每个 embedding Worker 并发为 1，避免重复模型副本与显存/内存竞争。

## 版本化索引

更新在新文档版本下生成完整分块和向量，全部成功才原子切换 current 可检索版本；旧版本随后异步清理。删除先在数据库事务中取消当前可检索资格，再投递清理任务，确保删除后不再召回。
